# /spec step 8: Done

`${CLAUDE_PLUGIN_ROOT}/skills/spec/SKILL.md` loads this file for `/spec done <spec>`. It runs under that skill's `allowed-tools`.

`${CLAUDE_PLUGIN_ROOT}` in this file is the plugin's root, the directory that holds its `skills/` and `hooks/`. Claude Code expands it in `SKILL.md` but not in a file you read, so in a Bash call write the absolute path, never the variable.

Run after the work items are built, from the repo, as `/spec done <spec>`. The build is the last and hardest test of a spec: it finds what reading, review and spikes didn't. This step writes that down, so the spec, its record and the research it came from say what is now true.

1. **Read** the spec, its record, and the research note in its frontmatter (if any). Take the repo, `read-at` and `cite-repo` as `finish` mode does.
2. **Find the build.** List the commits since the spec was first committed: `${CLAUDE_PLUGIN_ROOT}/hooks/git-read.py -C <repo> log --reverse --format='%h %ad %s' --date=short <first commit of the spec>..HEAD`, where the first commit is the last line of `${CLAUDE_PLUGIN_ROOT}/hooks/git-read.py -C <repo> log --follow --diff-filter=A --format=%h -- <spec>` (`--follow` finds it through a rename; a spec added twice prints both, oldest last). If that prints nothing, the spec was never committed (the skill leaves it for the user), so there's no range yet: ask in step 3 which commit the build started from. Read the messages, and the diffs of the files each work item lists, enough to tell which work items landed and where the build departed from the spec: a value, an approach, a dependency, a file, a Done when that changed or was dropped. Don't run the build or the tests; the user can.
   Also read the record's `## Evidence` section, which `/implement` writes: each work item's evidence line, the implement-verifier's table from its last round (a row with `PASS` passed; a round marked `refused` has none), and `implementer-run:` lines for the rows the verifier couldn't run. Keep the two apart. A verifier `PASS` is an independent check; an `implementer-run:` line is the implementer checking its own work, so a work item whose only passing evidence is such a line is *self-checked*, not independently verified. If the record has no `## Evidence` while a branch `implement/<safe basename>` exists, `<safe basename>` being what `${CLAUDE_PLUGIN_ROOT}/hooks/run-name.py '<spec basename>'` prints for the spec's filename without `.md`, as `/implement` names its branch (`${CLAUDE_PLUGIN_ROOT}/hooks/git-read.py -C <repo> branch --list implement/<safe basename>`), the build and its evidence are on that branch, not here: find its worktree with `${CLAUDE_PLUGIN_ROOT}/hooks/git-read.py -C <repo> worktree list`, tell the user to run `/spec done <absolute path of the spec in that worktree>`, in this same session (no need to start one in the worktree), and stop, changing nothing.
3. **Ask** in one AskUserQuestion call, with up to four questions, only what the commits can't settle: the commit the build started from, if step 2 found none; whether a work item that shows no commit landed some other way; whether the landed items' Done when checks have been run and passed (commits show that the work landed, not that it works), leaving out any the verifier's table records as `PASS`, and naming each self-checked one as run only by the implementer; and whether any cold review was run outside `/cold-review` or `/spec` (a pasted prompt) whose reply should be saved.
4. **Write the implementation notes** under the record's `## Implementation`, with the Edit tool, never a shell redirect, one line per departure: `- <YYYY-MM-DD>, <Wn> (<commit>): <what the build did differently, and why>`. Take the why from the commit message; if it gives none, say so. Save any review the user pastes under `## Cold review` (a full one) or `### Delta review, <date>` (a delta), unchanged, as step 6 would have. Don't rewrite the plan: once done, the spec is the record of what was planned, and the record says how it went.
5. **Status.** Set the spec's `status: done` if every work item landed and their Done when checks pass, by a verifier `PASS` or the user's answer; a self-checked work item counts only if the user's answer confirms it. Set `in-progress` if some haven't landed, or their checks haven't passed, been run, or been confirmed (name them, with their Done when commands, in the report); or `superseded` if the user says another spec replaced it. Leave the idea note's status alone.
6. **The research.** If a departure contradicts the research note's Recommendation or a Finding the Decision rests on (the build chose another option, a figure turned out wrong, a tool was dropped), say which, in one line each. Suggest `/research` to update the note, or `status: outdated` if the question itself has moved on. That call is the user's; change the note only if they say so, and then commit it in `~/notes` with the message `research: <title> (outdated by <spec basename>)`, naming it after `--` as `SKILL.md`'s *Link the notes* item does.
7. **Check.** Run `check-spec.py` on the spec, and `${CLAUDE_PLUGIN_ROOT}/skills/research/scripts/check-note.py` on the research note: a `related` path to a file the build deleted fails it. Fix those links in the note, and commit only that note, named after `--`. If `check-spec.py` fails only because an `in-progress` spec logs `Not reviewed:` changes with no delta review, don't edit around it: say so in the report and offer `/cold-review <spec>`.
8. **Report** one short line for each: the status, the work items landed, each self-checked work item by name, as checked only by the implementer, the number of implementation notes and the most important one, any research the build contradicts, and that the spec and record are left for the user to commit.
