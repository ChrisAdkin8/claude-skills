# /implement, part 2: the skill that implements a reviewed spec test first, its evals and docs

## Goal

Stage 5 of the workflow, Implement, becomes a skill. `/claude-skills:implement <spec>` (short name `/implement`) always hands the work to an `implementer` subagent: a headless Claude Code session of its own, which has seen none of the conversation, working on its own git worktree. It refuses a spec that isn't committed, reviewed and passing its checks. It saves a baseline of the repo's checks, then implements the work items in order: Done when red, code, Done when green, full suite, a scan of the staged diff, one commit. After the work items it applies `/simplify` and `/code-review medium --fix` as their own commits. Then the implement-verifier re-runs every Done when it can. The evidence lands in the spec's record on the implementation branch, where `/spec done`, run in the worktree, reads it. Prerequisite: part 1, `docs/specs/2026-09-26-implement-skill-1-tools.md`, whose tools this calls.

## Decision

No research note: the approach was settled in conversation on 2026-09-26, and the interview that day settled three questions the code left open. The spec was split in two after its cold review on 2026-09-27, when it passed 3,000 words: tools in part 1, the skill here. It was re-read at `1c7ea6e` on 2026-09-30, after the skills became a plugin.

- **The implementer always runs as a subagent, in its own headless session on the worktree** (settled with the user on 2026-09-27, replacing an implementer in the user's session). `/implement`, in the user's session, runs the gate, makes the worktree, writes a brief and launches the implementer with its working directory in the worktree, through a new launcher, `skills/implement/scripts/run-implementer.sh`. Its agent file is `hooks/agents/implementer.md`, passed per run as `run-agent.sh` passes its agents, through `agent-def.py` and `--agents` (`hooks/run-agent.sh:59-62`, `:75`, `:111`). It gets a new launcher because `run-agent.sh` runs only four named agents (`hooks/run-agent.sh:49-52`) under the agent sandbox, which denies Bash writes under `~/code` (`hooks/agent-sandbox.json:14`, restated at `hooks/agent-sandbox.md:8`) and refuses writes inside any directory named `.git` (`skills/spec/spiker.md:17`), so a sandboxed implementer could neither edit the repo nor commit. So the implementer runs outside the OS sandbox, as it would have in the user's session. Running in the worktree with the repo's own settings (`--setting-sources user,project`), it reads the repo's `CLAUDE.md`, runs its hooks, and commits straight to the branch. Rejected: a headless implementer in a scratch export whose commits `/implement` imports with `git am`, which has neither. Isolation comes from the separate session and the worktree; the OS sandbox guards the verifier (part 1).
- **`/simplify` and `/code-review medium --fix` are applied, each as its own commit, then everything is re-tested.** A fix that breaks a test or a Done when is reverted and named in the report. The level is `medium` (settled with the user on 2026-09-30): `/code-review` otherwise reuses the level last typed, which a headless session doesn't have *(assumption)*, and `--fix` applies every finding unwatched, so the level that reports only findings it is fairly sure of is the one to use. Rejected: report-only, which leaves known cleanups undone; `high` or above, which adds uncertain findings that `--fix` would apply.
- **`/implement` never commits on the user's branch.** The spec, its record and its spike results must already be committed; `/implement` stops and says so if they aren't.

## Non-goals

- Pushing, opening a pull request, or merging. `/implement` leaves a branch.
- Implementing work items in parallel.
- Running the implementer under an OS sandbox (see Decision).
- Repos outside `~/code`, or not in git.
- Changing the spec's plan. `/implement` logs departures in the record; the spec stays the plan.

## Design

```mermaid
flowchart TD
  G[Gate: spec committed, reviewed, check-spec PASS, no DRIFT at HEAD] --> W[git worktree + branch implement/basename, or reuse them to resume]
  W --> A[Launch the implementer subagent in the worktree: run-implementer.sh]
  A --> B[Baseline: repo checks, saved]
  B --> L{Next work item}
  L --> R[Done when: red]
  R --> I[Implement, up to 3 attempts]
  I --> S[Full suite; stage; scan-diff.py --base item start]
  S -->|flag or design change| X[Stop: reply with the question; /implement asks the user and resumes it]
  S --> C[Commit Wn, record line]
  C --> L
  L -->|none left| Q[/simplify, /code-review --fix: own commits, re-test]
  Q --> V[/implement runs the implement-verifier, then resumes the implementer for the CANNOT-RUN rows]
  V --> E[Evidence in record ## Evidence; report: run /spec done in the worktree]
```

- **Gate.** In order, stopping at the first failure with what to do: `git status --porcelain -- <spec> <record> <spike results>` is empty, so all three are committed at HEAD (else: commit them, then re-run); the status is `reviewed`; `check-spec.py` prints `RESULT: PASS`; `check-spec.py --drift-at HEAD` (part 1) prints no `DRIFT:` line (else: run `/spec finish <spec>`, which re-reads those ranges and moves read-at, W5). It checks HEAD, not the working tree, because the worktree starts from HEAD: other uncommitted files in the checkout are left alone and named in one line. Files the file-level drift WARN names without a `DRIFT:` line are logged under `## Evidence`.
- **The subagent.** Once the gate passes and the worktree exists, `/implement` writes a brief (the spec, record and worktree paths, the baseline command list's location, and today's date) to `~/.cache/implement-runs/<repo dir>--<basename>/implementer/brief.md` and runs `run-implementer.sh <worktree> <run dir>` with `run_in_background`, as `hooks/run-agent.md` says for agents. The launcher finds the plugin root from its own location, refuses a working directory that isn't a worktree of a repo under `~/code`, renders the agent file with `agent-def.py --root <plugin root>`, and runs `claude -p --agents <run dir>/agents.json --agent implementer` there with `--setting-sources user,project`, `--permission-mode acceptEdits`, the agent's tools pre-approved, `--max-budget-usd` $20 (`IMPLEMENT_MAX_USD` overrides it) *(assumption: seven work items fit in $20)*, and `--resume` for follow-ups. The cap is for the whole run: each call's `run.json` is kept as `run-<n>.json`, each resume gets the cap less the `total_cost_usd` already spent, and a resume once that reaches the cap is refused. Like `run-agent.sh`, it reads `brief.md` (or `followup.md` with `--resume`), writes `reply.md`, `run.json`, `run.err` and `session_id` to the run dir (`hooks/run-agent.sh:86-98`, `:111-135`, `:154-160`), and exits 0 with a reply in shape, 2 when the run never started (a bad path, no session to resume, the cap spent), 3 when the reply's last line isn't one of `Implementer: done`, `Implementer: question: <text>` or `Implementer: stopped: <reason>`, and otherwise with no reply. `hooks/agents/implementer.md` has `name`, `description` and `tools: Read, Edit, Write, Glob, Grep, Bash, Skill`, and no hooks, since the guard's hooks are for the read-only agents; pre-approving Bash also lets `/simplify` and `/code-review` run their own checks, which spike S2 found refused without it. The steps from Baseline to Clean-up are the implementer's, in its agent file; `/implement` only frames, relays and verifies. A headless session can't ask the user anything, so wherever a step below stops to ask, the implementer ends its reply with the question instead; `/implement` asks it with AskUserQuestion and resumes the implementer with the answer.
- **Worktree.** `git worktree add <repo>/../<repo dir>-worktrees/<spec basename> -b implement/<spec basename>`, then work only there. The first commit on the branch sets the spec's `status: in-progress` and starts `## Evidence` with `- Started at <HEAD it branched from>`.
- **Resume.** If branch `implement/<basename>` already exists, `/implement` resumes it instead: it reuses the worktree, or re-adds it with `git worktree add <path> implement/<basename>` (no `-b`) if the directory is gone, and runs the Gate there, where the status must be `in-progress` and drift is checked with `--drift-at <the Started at commit>`, so the branch's own commits never count as drift. The implementer starts at the first work item with no commit ending `(Wn)`.
- **Baseline.** The repo's checks come from its `CLAUDE.md`, `AGENTS.md`, CI workflows, Makefile or Taskfile, and pre-commit config. Output goes to `~/.cache/implement-runs/<repo dir>--<basename>/baseline.txt`, and one summary line per check to the record. A check failing at baseline may stay failing, but may not get worse.
- **Each work item.** Note its starting commit. Make its Done when observable first and see it fail; a Done when that already passes stops the run (the item is done, or the check can't see the change). Implement, at most three attempts to turn it green. Run the baseline checks. `git add -A`, then `scan-diff.py --base <starting commit> --files <the item's Files, the spec, its record, and any logged departure's files>`: the spec and record are always passed, since the implementer edits both. Commit as `<area>: <what> (Wn)`, with the area the repo's convention asks for, and append to the record's `## Evidence`: `- Wn (<commit>): Done when <command> -> <result>; suite <pass | n failing, as baseline>; scan <clean | flags>`. That line names its own commit, so it's written after it and goes into the next commit.
- **Departures.** A small one (a helper, a renamed function, an extra file the item needs) is allowed: log it first as an `## Implementation` line in `done-step.md`'s format, then pass its file to `--files`. A change to the Design, the Decision or a Done when, a third failed attempt, or any other scan flag stops the run: the implementer replies with the question, which `/implement` puts to the user with AskUserQuestion; unattended, it stops and reports.
- **Clean-up.** `/simplify`, then `/code-review medium --fix`, each committed separately (`<area>: simplify after implementing`, `<area>: code-review fixes`). Then the suite and every Done when again; a fix that breaks one is reverted with `git revert` and named in the report.
- **Verify.** `prepare-verify.sh` on the branch's first and last commits, copy in the spec, record and a brief, then `run-verify.sh` in the background (part 1). Copy its table under `## Evidence`. `/implement` runs it, so the verifier's brief comes from a session that didn't write the code. For each `CANNOT-RUN` row, `/implement` resumes the implementer, which runs that Done when itself in the worktree and adds a `implementer-run:` line with the command and result, kept apart from the verifier's table. On `Implementation holds: no`, fix what it names and run it once more, in `V2`; there is no third round.
- **Evidence and hand-off.** `## Evidence` holds all of the above and lives on the implementation branch. Once the verifier's table and the `implementer-run:` lines are in, `/implement` commits the record in the worktree as `<area>: implementation evidence`, the branch's last commit, so nothing is left uncommitted. The verifier ran on the commit before it, which changes only the record. so the report, one short line per item, says to run `/spec done <spec>` from the worktree. `/implement` doesn't push.

## Risks and rollback

- **The implementer runs the repo's code outside the OS sandbox, with no one watching.** Headless, its allowed tools run without asking, and the guard doesn't cover it; only its working directory and brief keep it to the worktree. `/implement` is for the user's own repos and reviewed specs; the sandboxed verifier is the independent check.
- **Implement eval cases run outside the OS sandbox** (W4), on fixtures their `setup.sh` builds.
- **Cost.** An implementation run is one subagent session, capped at $20 across all its resumes, plus up to two verifier runs at $5 each; the report gives each run's cost from its `run.json`.
- **Rollback:** delete `skills/implement/`, `hooks/agents/implementer.md`, `tests/test_run_implementer.py`, `tests/skill-evals/implement-case-settings.json` and the three new eval cases, and revert W5's edits and W4's `run.sh` changes; `/spec` then gives its old prompt. An implementation run's worktree and branch are removed with `git worktree remove` and `git branch -D`.
